# Гайд о проекте OFDM

Собственный OFDM-приёмопередатчик для PlutoSDR с синхронизацией по PSS, компенсацией CFO, оценкой канала и демодуляцией полезных данных.

## Что именно делает программа

Проект работает в нескольких режимах:

- `simulation`  
  полностью моделирует систему без SDR и показывает графики;
- `TX`  
  передаёт OFDM-кадр в эфир;
- `RX`  
  принимает один захват, находит кадр и декодирует его;
- `realtime TX`  
  открывает окно управления передатчиком;
- `realtime RX`  
  показывает непрерывный приём, временную область, созвездие и оценку канала.

## Логика кадра

Кадр состоит из трёх логических частей:

1. `PSS`  
   известная заранее синхропоследовательность, по которой приёмник ищет начало кадра;
2. `training OFDM symbol`  
   обучающий OFDM-символ, который известен приёмнику и используется для оценки канала;
3. `payload OFDM symbols`  
   полезные OFDM-символы с текстом.

Внутри OFDM-символа:

- часть поднесущих нулевые;
- одна центральная поднесущая `DC` не используется;
- часть поднесущих занята пилотами;
- остальные поднесущие несут полезные данные.

## 4. Математическая модель

Главная модель в частотной области:

`Y[k] = H[k] * X[k] + W[k]`

где:

- `X[k]` — переданный символ на `k`-й поднесущей;
- `H[k]` — комплексная частотная характеристика канала;
- `W[k]` — шум;
- `Y[k]` — принятый символ.

Задача приёмника:

1. найти начало OFDM-кадра;
2. оценить `H[k]`;
3. оценить и компенсировать частотный сдвиг;
4. восстановить `X[k]` по `Y[k]`.

После оценки канала эквализация делается так:

`X_hat[k] = Y[k] / H_hat[k]`

Если `H_hat[k]` близка к настоящему `H[k]`, точки созвездия собираются около идеальных позиций и демодуляция проходит корректно.

## Передача: что происходит шаг за шагом

### Текст превращается в полезную нагрузку

Текст переводится в байты.
В payload добавляются:

- magic bytes;
- длина текста;
- сам текст;
- CRC.

Это нужно, чтобы на приёме можно было:

- проверить, что пакет вообще наш;
- понять длину сообщения;
- проверить правильность декодирования по CRC.

### Байты превращаются в биты

Байты упаковываются в битовый поток.

### Биты модулируются

Биты превращаются в комплексные символы выбранной модуляции.

Поддерживаемые варианты в архитектуре проекта:

- `BPSK`
- `QPSK`
- `QAM16`
- `QAM64`

### Полезные символы раскладываются по поднесущим

В частотной области формируется OFDM-символ:

- пилоты ставятся в заранее известные позиции;
- полезные символы ставятся в информационные поднесущие;
- по краям и в центре остаются нули.

### Переход во временную область

После этого применяется `IFFT`, и частотное представление переводится во временную область.

### Добавление циклического префикса

К OFDM-символу добавляется `CP` — циклический префикс.

Он нужен для двух задач:

1. борьбы с межсимвольной интерференцией в многолучевом канале;
2. удобной синхронизации, потому что начало символа и его конец совпадают по структуре.

### Сборка полного кадра

Полный TX-кадр выглядит так:

`[PSS + CP] + [training OFDM + CP] + [payload OFDM + CP] + ...`

### Передача в PlutoSDR

Готовый массив комплексных отсчётов подаётся в поток `SoapySDR`, и устройство начинает передачу.

## Приём: что происходит шаг за шагом

### Захват IQ-отсчётов

PlutoSDR принимает поток комплексных отсчётов `I/Q`.

### Поиск кадра по PSS

Приёмник знает PSS заранее, поэтому строит корреляцию:

- скользит эталонный PSS по принятому буферу;
- ищет максимум корреляции;
- выбирает наиболее вероятное начало кадра.

Если говорить простыми словами:

> Приёмник пытается найти место, где принятый сигнал максимально похож на заранее известный синхросигнал.

### Грубая оценка CFO

Одновременно с поиском PSS приёмник оценивает грубый `CFO` — смещение несущей частоты.

Это нужно, потому что у передатчика и приёмника локальные генераторы не идеально совпадают, и без компенсации точки созвездия начинают вращаться.

### Выделение training и payload

После того как найден старт кадра, структура кадра уже известна:

- где заканчивается PSS;
- где начинается training;
- где начинается payload.

То есть дальше можно просто вырезать нужные куски массива по индексам.

### Тонкая оценка CFO

После грубой компенсации выполняется более тонкая подстройка по OFDM-структуре training-символа.

### Удаление CP и FFT

У каждого OFDM-символа:

1. отбрасывается циклический префикс;
2. применяется `FFT`;
3. сигнал переводится обратно в частотную область.

Именно в частотной области дальше работает оценка канала и демодуляция.

## Оценка канала

В проекте реализовано несколько методов оценки канала.

### Training LS

Используется известный training-символ:

`H_hat[k] = Y_train[k] / X_train[k]`

Плюсы:

- простота;
- понятная математика;
- хорошая базовая точка.

Минусы:

- шум напрямую попадает в оценку.

### Pilot LS Linear

Оценка строится только по пилотам, потом интерполируется на остальные активные поднесущие.

Сначала:

`H_hat[p] = Y[p] / X[p]`

Потом между пилотами делается линейная интерполяция.

Плюс:

- очень дёшево вычислительно.

Минус:

- если канал меняется по частоте быстро, интерполяция начинает ошибаться.

### Pilot LMMSE

Это более “умная” пилотная оценка, которая учитывает статистику канала и шум.

Формально:

`H_hat = R_hp * (R_pp + sigma^2 I)^(-1) * H_ls`

Плюс:

- лучше подавляет шум, чем обычный LS.

Минус:

- сложнее и требует априорных предположений о корреляции канала.

### DFT LS

Идея такая:

1. сначала получить частотную LS-оценку;
2. перейти во временную область;
3. отбросить “хвост” импульсной характеристики длиннее CP;
4. вернуться обратно в частотную область.

Плюс:

- хорошо подавляет шум;
- физически логичен для OFDM, потому что полезная длительность канала не должна превышать CP.

Минус:

- переходы из областей

### Decision Directed

После первичной оценки канала:

1. символы эквализуются;
2. по ним принимаются жёсткие решения;
3. по этим решениям можно дополнительно уточнить канал.

Плюс:

- может улучшать результат при хорошем SNR.

Минус:

- если первые решения ошибочны, можно ухудшить результат.

## Почему вообще нужен CP

Циклический префикс — это копия конца OFDM-символа, добавленная в начало.

Он нужен, чтобы многолучевое распространение не разрушало ортогональность поднесущих в полезной части символа.

Если длительность канала меньше длины CP, то после удаления префикса линейная свёртка канала превращается в циклическую, а это идеально подходит для обработки через FFT.

## Почему нужен PSS

Без PSS приёмник не знает:

- где начинается кадр;
- от какого индекса правильно резать training и payload;
- где именно выполнять FFT.

То есть PSS — это точка входа во всю синхронизацию.

## Что такое CFO и почему он опасен

`CFO` — это carrier frequency offset, рассогласование частоты несущей между TX и RX.

Он приводит к:

- вращению созвездия;
- межподнесущим помехам;
- ухудшению оценки канала;
- ошибкам демодуляции.

Поэтому в проекте есть:

- грубая компенсация CFO;
- тонкая компенсация CFO.

## Что происходит перед демодуляцией

Последовательность такая:

1. найден старт кадра;
2. компенсирован CFO;
3. выполнена FFT;
4. оценён канал;
5. выполнена эквализация;
6. выполнена коррекция остаточной фазы/масштаба по пилотам;
7. только после этого точки идут в демодулятор.

Именно это место критично для качества созвездия.

Если здесь всё сделано правильно, точки собираются возле идеальных позиций.

## Потоки и realtime-архитектура

Это важный момент, потому что проект не просто “один раз принял массив и всё”.

В realtime-режиме есть разделение на backend и frontend.

### Поток TX

Поток передатчика:

- держит открытым устройство TX;
- получает уже собранный OFDM-кадр;
- циклически отправляет его в эфир.

### Поток RX stream

Этот поток:

- непрерывно читает IQ-отсчёты из PlutoSDR;
- хранит окно последних принятых семплов;
- считает live-метрики;
- готовит данные для графиков.

### Поток RX decode

Этот поток:

- берёт уже накопленный буфер;
- пытается найти полноценный кадр;
- запускает синхронизацию, CFO, FFT, оценку канала и декодирование.

### GUI-поток

GUI-поток не должен заниматься тяжёлой математикой.

Поэтому сейчас сделано так:

- backend-потоки заранее готовят массивы для графиков;
- ImGui только рисует готовые данные.

Это снижает нагрузку на процессор и делает realtime-интерфейс стабильнее.

## Что сказать, если спросят про ограничения

Честный ответ:

- система учебная, а не промышленная;
- параметры поднесущих и кадра зафиксированы;
- нет помехоустойчивого кодирования типа convolutional/LDPC;
- при сложном реальном канале качество сильно зависит от точности оценки канала и синхронизации;
- для высоких порядков QAM требования к SNR и качеству эквализации заметно выше.

## Что говорить, если спросят, почему именно OFDM

Потому что OFDM:

- удобно работает в частотно-селективном канале;
- позволяет превратить сложную задачу эквализации широкополосного канала в набор более простых задач по отдельным поднесущим;
- очень хорошо сочетается с пилотами, CP, FFT и оценкой канала.

## Самые вероятные вопросы преподавателя

### Что делает PSS?

Позволяет найти начало кадра по корреляции.

### Зачем нужен training-символ?

Чтобы получить опорную оценку канала по известному символу.

### Зачем нужен циклический префикс?

Чтобы сохранить ортогональность поднесущих в многолучевом канале и упростить работу через FFT.

### Что такое CFO?

Рассогласование частот генераторов TX и RX, из-за которого вращается созвездие и ухудшается демодуляция.

### Что такое эквализация?

Это компенсация влияния канала по оценке `H[k]`, обычно через деление `Y[k] / H_hat[k]`.

### Почему точность оценки канала так важна?

Потому что ошибка в `H_hat[k]` напрямую переносится в ошибки положения точек созвездия и дальше в битовые ошибки.
